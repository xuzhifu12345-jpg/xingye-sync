# 千帆云递 · 桌面客户端打包方案（exe / dmg / AppImage）

> 目标：把当前「整合包 + start 脚本」的交付方式，升级为**双击即装的桌面应用**，
> 内置 **Git / Python / Node.js / CloakBrowser（指纹浏览器）** 四类运行时，
> 并提供与「安全中心」截图一致的**运行时设置界面**（开关 / 版本 / 路径 / 审计日志）。
> 覆盖 **Windows、Linux、macOS** 三端。

---

## 0. 结论摘要（TL;DR）

| 决策项 | 结论 |
|--------|------|
| 客户端外壳 | **Electron + electron-builder**（理由见 §2.2） |
| 后端 | 保持 **Python Flask 不动**，用 **python-build-standalone** 便携运行时运行（不再要求用户装 Python / venv） |
| 前端 | 改为 **Flask 直接托管 `frontend/dist`**（生产模式），彻底去掉 Vite dev server 和 130MB `node_modules` |
| MCP | 用 **Electron 内置 Node**（`ELECTRON_RUN_AS_NODE=1`）运行 `dist/index.js`，系统 Node 退化为"可选运行时" |
| 运行时存放 | **不放安装目录**，放用户数据目录（`%LOCALAPPDATA%` / `~/Library/Application Support` / `~/.local/share`），**manifest 驱动、可独立升级** |
| 安装包形态 | **离线完整包（唯一形态）**：四类运行时 + ffmpeg 全部内嵌在安装包里，首启解压到用户数据目录，**不依赖 CDN/网络**；安装包大（Windows ≈ 700MB / Linux ≈ 850MB / macOS ≈ 450MB）。CDN 通道保留为"运行时独立热更新"的备用通路（§7 C 通道，可关） |
| 代码签名 | **当前未采购证书**：Windows 走签名积累（用户点"仍要运行"过渡）；macOS 是硬阻塞（见 §6.3 第 5 点，临时跳过 macOS 或先采购 Apple Developer ID） |
| 更新 | **双通道**：① 主程序走 electron-updater；② 业务代码（backend + frontend/dist + mcp/dist）走轻量资源包热更新，保留现在「git pull 秒级更新」的体验 |
| 体积预期 | 安装后 **Windows ≈ 1.4GB / Linux ≈ 1.5GB / macOS ≈ 1.1GB**；离线完整包 **≈ 600–900MB**（估算见 §5.5） |

**一处需要你拍板的地方**（详见 §12）：**Python 在设置界面里要管到什么程度？**（最小是"路径切换 + 显示版本/状态"，复杂是"多版本切换 + venv 管理"，直接影响 §5.2 卡片 UI 与 §5.5 API 形态）。其他待定项（macOS 分发策略、CDN 是否启用、Linux 支持矩阵）见 §12。

## 1. 现状盘点

### 1.1 当前交付链路

```
用户下载网盘整合包
  └─ QianFan Sync/
      ├─ dependency/{python,git,node,cloakbrowser,bin}/   ← scripts/pack-deps.sh 生成
      ├─ start.bat / start.sh / start-macos.sh
      └─ (首次运行时 git clone 仓库代码到本目录)
```

- `scripts/pack-deps.sh` 只打包**运行时**，**不含业务代码**；
- `start.bat` / `start.sh` 首次运行 `git clone` 仓库，之后每次启动 `git fetch + reset --hard` 强更；
- 启动三个进程：后端 Flask（5409，支持 `SAU_PORT` 覆盖）、前端 Vite dev server（5173）、MCP（5410，Node/TS）；
- 数据目录 `data/`，打包模式用环境变量 `SAU_DATA_DIR` 覆盖（`backend/conf.py` 已支持）；
- 浏览器二进制通过 `CLOAKBROWSER_BINARY_PATH` 注入。

### 1.2 用户为什么会卡住（真实痛点）

| 痛点 | 现状 | 桌面化后 |
|------|------|----------|
| 不知道点哪个文件 | 压缩包里有 `start.bat`、`start.sh`、`start-macos.sh`、`dependency/`，选错就报错 | 安装后有开始菜单/桌面图标，双击即用 |
| 首次启动要连 GitHub | `git clone` 失败即整个流程终止（国内网络常见） | 代码随包内嵌，**完全脱离 GitHub** |
| 黑窗口闪退看不到原因 | `cmd` 窗口一闪而过，用户无法自查 | 图形化启动进度 + 日志导出 + 错误弹窗（带"复制诊断信息"） |
| 杀软/系统拦截 | 无签名 exe、`.bat` 被拦 | 代码签名 + 白名单提交（当前无证书：见 §6.4 临时方案） |
| 端口/进程残留 | 反复启动遗留 `python.exe` / `chrome.exe` | 单实例锁 + 子进程树统一收割 |
| 卸载/升级麻烦 | 手动删目录 | 标准卸载器 + 自动更新 |

### 1.3 必须保留的东西

- **现有 `start.*` 脚本与整合包流程不能废**：老用户升级路径要平滑，且开发同学仍然需要脚本方式跑（CI/服务器部署也依赖）。
- **业务代码热更新能力**：现在改一行后端代码，用户下次启动就生效。桌面版必须用「资源包热更新」等价替代，否则每次改动都要让用户重下几百 MB 安装包。

## 2. 目标形态与技术选型

### 2.1 三端产物

| 平台 | 安装器 | 产物 | 说明 |
|------|--------|------|------|
| Windows | **NSIS**（electron-builder 内置） | `QianFanSync-Setup-1.3.0-x64.exe` | 默认装到 `%LOCALAPPDATA%\Programs\QianFanSync`（免管理员）；可选 perMachine 装 `Program Files` |
| Linux | **AppImage + deb**（可选 rpm） | `QianFanSync-1.3.0-x86_64.AppImage` / `.deb` | deb 声明 `Depends:` 系统库；AppImage 首启做依赖体检 |
| macOS | **dmg + zip**，**arm64 与 x64 分开出** | `QianFanSync-1.3.0-arm64.dmg` / `-x64.dmg` | 不做 universal：CloakBrowser 是分架构二进制，合包等于塞两份 Chromium。**当前未采购 Developer ID → 见 §6.3 第 5 点硬阻塞** |

### 2.2 为什么是 Electron（而不是 Tauri / pywebview）

| 方案 | 优点 | 为什么不选 / 备选理由 |
|------|------|----------------------|
| **Electron（推荐）** | 打包/签名/公证/自动更新/托盘/单实例生态最成熟；Vue 前端零改动；Chromium 自带，不受系统 WebView 影响；团队已有 Node 经验（backend-mcp） | 体积 +~200MB。相对于本方案 1.4GB 的运行时体量，这 200MB 不是瓶颈 |
| Tauri v2 | 壳只有 ~10MB | Windows 依赖 **WebView2 运行时**（Win10 老机器常缺，要额外带 Bootstrapper ~50MB，优势被吃掉）；Linux 依赖 **WebKitGTK**，发行版差异大；还要引入 Rust 工具链与 sidecar 交叉编译，**排障成本高** |
| pywebview + PyInstaller | 单语言（Python） | PyInstaller 打 `opencv + playwright/cloakbrowser` 子进程极易踩坑；macOS 上「签名后的 .app 内嵌未签名 Chromium」用 PyInstaller 处理非常痛苦；**没有成熟的自动更新/托盘/单实例方案**，全要自己写 |

> 关于体积的额外说明：Electron 自带 Node，**MCP 服务可以直接用它跑**（`ELECTRON_RUN_AS_NODE=1`），因此"内置 Node"这个运行时严格说只为「用户/AI Agent 需要独立 node 命令」服务，可以默认下载、也可不装。

## 3. 总体架构

### 3.1 进程模型

```
┌─────────────────────────────────────────────────────────────┐
│ Electron 主进程（QianFanSync 外壳）                          │
│  · 单实例锁 / 托盘 / 主窗口 / 启动画面                        │
│  · 运行时管理器：探测 → 校验 → 解压 → 生成 env                │
│  · 生命周期：拉起后端 → /api/health 就绪 → 打开界面           │
│  · 更新器：主程序更新 + 资源包热更新                          │
│  · 退出：收割整棵子进程树                                     │
└───────┬───────────────────────────┬─────────────────────────┘
        │ spawn(env)                │ spawn(env)
        ▼                           ▼
┌───────────────────┐      ┌──────────────────────┐
│ Python 后端        │      │ MCP 服务（Node）      │
│ python-standalone  │      │ 端口 5410，可选启用    │
│ 端口 5409(可回退)  │      └──────────────────────┘
│ 托管 frontend/dist │
└─────────┬─────────┘
          │ spawn（Playwright 协议）
          ▼
┌───────────────────────────────┐
│ CloakBrowser Chromium 子进程   │
│ CLOAKBROWSER_BINARY_PATH 注入  │
└───────────────────────────────┘
```

**关键点**：外壳**不做业务**，只做「环境装配 + 生命周期 + 原生能力桥」。
这样三端只有一份业务代码，网页模式（浏览器直接访问 127.0.0.1:5409）依然可用，出问题能一键退回老流程。

### 3.2 目录布局

**安装目录（只读，随主程序升级）**
```
Windows: %LOCALAPPDATA%\Programs\QianFanSync\      (macOS: /Applications/QianFanSync.app)
├── QianFanSync.exe
└── resources/
    ├── app.asar              # 外壳代码（含启动画面、托盘、运行时管理器）
    └── runtime-seed/           # 离线完整包模式下：四类运行时 + ffmpeg 的已解压目录树，首启由外壳 copy 到用户数据目录（无需 7z 工具链）
```

**用户数据目录（可写，可迁移，可独立升级）**
```
Windows: %LOCALAPPDATA%\QianFanSync\        (macOS: ~/Library/Application Support/QianFanSync)
├── app-code/                 # 业务代码包（热更新目标）
│   ├── backend/              # 含 frontend/dist（Flask 托管）
│   ├── frontend-dist/
│   ├── mcp/dist/
│   └── version.json          # 资源包版本 + sha256（支持回滚上一版）
├── runtime/                  # 四类内置运行时（manifest 驱动）
│   ├── python/  node/  git/  cloakbrowser/
│   ├── ffmpeg/               # 视频帧抽取刚需
│   ├── manifest.json         # 当前安装清单（版本/校验和/来源）
│   └── .download/            # CDN 备用通道的断点续传临时目录
├── data/                     # ← SAU_DATA_DIR 指向这里（db / cookies / uploads / logs）
├── logs/                     # shell.log / backend.log / mcp.log（滚动切割）
└── config.json               # 运行时开关、路径覆盖、端口、更新通道
```

**为什么运行时和业务代码都放用户目录？**
1. macOS：公证后的 `.app` 一旦被修改，**代码签名立即失效**，必须放 bundle 外；
2. Windows：装到 `Program Files` 时非管理员无写权限，热更新/下载会失败；
3. 主程序升级（换 Chromium/Electron）与运行时升级（换 CloakBrowser 版本）解耦，互不牵连。

### 3.3 启动时序

```
1 单实例检查（已有实例 → 聚焦已有窗口并退出）
2 读 config.json + runtime/manifest.json
3 运行时体检（并行、不阻塞）：
    python 必需 → 缺失则进入「首次运行向导」
    其余按开关状态校验（版本 + sha256 + 可执行权限）
4 首次运行向导（仅首次/缺组件）：
    检测 runtime/ 是否已就绪 → 缺失则从安装目录 resources/runtime-seed/ 复制（**已解压形态**，无需 7z）
    或 → 走 §4.2 的 CDN 备用通道下载（多镜像回退 + 断点续传；需要 zip/tar 解压）
5 就绪后：生成 env（PATH 前置、SAU_DATA_DIR、SAU_PORT、CLOAKBROWSER_BINARY_PATH）
6 spawn 后端 → 轮询 /api/health（超时 60s，展示启动日志尾部）
7 打开主窗口（BrowserWindow 加载 http://127.0.0.1:<port>）+ 托盘常驻
8 后台：检查资源包更新 / 主程序更新（静默，成功后提示重启）
```

## 4. 运行时（4 个内置环境）方案

### 4.1 来源与体积总表

| 运行时 | Windows 来源 | Linux 来源 | macOS 来源 | 解压后体积 |
|--------|--------------|-----------|-----------|-----------|
| **Python 3.12** | `astral-sh/python-build-standalone`（install_only） | 同上（linux-gnu） | 同上（darwin） | ~80MB + 依赖 ~170MB |
| **Node.js 22 LTS** | nodejs.org `win-x64.zip` | `linux-x64.tar.xz` | `darwin-{arm64,x64}.tar.gz` | ~80–110MB |
| **Git** | **MinGit**（已敲定，仅 `git`） | 系统包（deb `Depends: git`）；AppImage 走启动体检 | 系统自带 `/usr/bin/git`；如需新版用 Xcode CLT/静态构建 | ~60MB |
| **CloakBrowser** | 已有 `cloakbrowser-windows-x64.zip` | 已有 `cloakbrowser-linux-x64.tar.gz` | 已有 `cloakbrowser-darwin-{arm64,x64}.tar.gz` | **536 / 696 / 350 / 368 MB** |
| （附带）ffmpeg + ffprobe | gyan.dev essentials | johnvansickle static | evermeet.cx | ~150MB |

> **已确认可用**：`D:\work\配套指纹浏览器\` 下四个包齐全，macOS 两个架构都有——这解决了 `pack-deps.sh` 里「macOS 需用户自备离线包」的历史遗留问题。
> 版本差异需登记在 manifest 里（win=146.0.7680.177.5，mac=145.0.7632.109），**不要假设三端同版本**。

### 4.2 运行时清单（manifest.json）

```jsonc
{
  "schema": 1,
  "generatedAt": "2026-09-17T12:00:00Z",
  "items": [
    {
      "id": "cloakbrowser",
      "displayName": "CloakBrowser 指纹浏览器",
      "required": false,
      "platforms": {
        "win-x64":   { "version": "146.0.7680.177.5",
                       "localPath": "runtime/cloakbrowser/chrome.exe",
                       "bin": "chrome.exe",
                       "sha256": "…" },
        "mac-arm64": { "version": "145.0.7632.109",
                       "localPath": "runtime/cloakbrowser/Chromium.app",
                       "bin": "Chromium.app/Contents/MacOS/Chromium" },
        "mac-x64":   { "…": "…" },
        "linux-x64": { "version": "146.0.7680.177.5", "bin": "chrome" }
      },
      // 可选 CDN 备用通道（默认离线完整包不依赖）
      "cdn": {
        "enabled": false,
        "url": "https://cdn.<your-domain>/runtime/cloakbrowser-{platform}.zip",
        "mirrors": ["https://oss.<your-domain>/..."]
      }
    },
    { "id": "python",  "required": true,  "…": "…" },
    { "id": "node",    "required": false, "…": "…" },
    { "id": "git",     "required": false, "…": "…" },
    { "id": "ffmpeg",  "required": false, "…": "…" }
  ]
}
```

- **离线完整包默认走 `localPath`**（首启从 `runtime-seed/` 解压到 `runtime/`），**不走 CDN**；
- `cdn.enabled=false` 是默认安全选择；只有需要「不重装就升级 CloakBrowser」时才开（见 §7 C 通道）；
- 每个包带 `sha256` + `size`，解压/下载后强校验；
- manifest 本身也走「先查最新 → 对比本地」流程，因此**升级 CloakBrowser 只需换安装包内的 `runtime-seed/`**，不必发新版安装包（除非主程序也变了）。

### 4.3 环境变量注入规则（后端零改动即可生效）

| 变量 | 值 | 已有支持 |
|------|-----|---------|
| `PATH` | `runtime/bin` 前置 + 各运行时子目录 | 现有 `start.bat` 已用同款做法 |
| `SAU_DATA_DIR` | 用户数据目录 / data | `backend/conf.py` ✅ |
| `SAU_PORT` | 默认 5409，占用时自动回退 | `backend/app.py:1853` ✅ |
| `CLOAKBROWSER_BINARY_PATH` | 按平台解析出的二进制绝对路径 | 现有脚本 ✅ |
| `PYTHONHOME` / `PYTHONPATH` | 便携 Python 定位（避免串到系统 Python） | 需在壳里设置 |
| `PLAYWRIGHT_BROWSERS_PATH` | 指向 runtime/cloakbrowser（若 wrapper 走 Playwright 解析） | 需确认 |

后端里 `ffmpeg_service._find_binary()` 已经「先 `shutil.which` 再回退」，所以 **PATH 前置即可命中内置 ffmpeg**；运行时管理器只需要保证「开关关掉时，注入的路径也一并撤掉」。

### 4.4 每个运行时的"被谁依赖"

在设计开关语义前必须先有这张表（否则用户关了 Node，功能静默坏掉）：

| 运行时 | 依赖方 | 关闭后果 |
|--------|--------|---------|
| **Python** | 后端本体 | **不可关闭**（UI 标注「必需」，仅允许切路径） |
| **CloakBrowser** | 登录、发布、合集/话题抓取（19 平台绝大部分 `impl/*`） | 核心功能不可用，UI 顶部横幅提示 |
| **Node** | MCP 服务（AI Agent 集成） | MCP 不启动；若壳用自带 Node 兜底则「降级可用」 |
| **Git** | 资源包热更新的兜底通道、未来的插件/适配器拉取 | 仅影响更新兜底，不影响发布 |
| **ffmpeg** | 视频时长识别、封面帧抽取（`materials_bp`、`test_video`） | 视频相关功能静默失效 → 必须给"未安装"提示，不能默默失败 |

## 5. 设置界面设计（对齐截图）

### 5.1 信息架构

在现有 `frontend/src/views/Settings.vue` 之外**新增一级页面**「安全中心 / 运行时」，采用截图的**左导航 + 右内容**两栏布局：

```
设置
├── 通用 / 个性化 / 任务 / 通知 …（现有卡片保留）
└── 安全中心                       ← 新增
    ├── 内置运行时      （总开关 + 4 张运行时卡片：Git / Python / Node.js / CloakBrowser）
    ├── 依赖与降级      （谁依赖谁、当前哪些功能被禁用）
    ├── 审计中心        （命令执行/放行记录：导出、清空）
    └── 存储与目录      （运行目录、占用、迁移、打开目录）
```

### 5.2 运行时卡片（截图里 Node.js / Python / Git Bash 那一组）

每个运行时的字段与交互：

| 元素 | 说明 |
|------|------|
| 图标 + 名称 + 一行说明 | 与截图一致（如「基于 Chrome V8 引擎的 JavaScript 运行时，用于服务端开发」） |
| 状态徽标 | 就绪（绿）/ 未安装（灰）/ 校验失败（红）/ 版本过旧（黄）/ 必需（蓝） |
| 版本号 | 来自实测（执行 `--version`），不是写死的字符串 |
| 总开关 | 「允许使用随包提供的运行时工具」——关闭后全部回退系统/自定义路径 |
| 单项开关 | 启用/禁用该内置运行时（禁用 → 依赖功能降级并提示，不做静默失败） |
| 模式选择 | 内置（随包）/ 系统（PATH 探测）/ 自定义路径（文件选择器） |
| 操作按钮 | 检测、修复、打开目录、查看日志 |
| 体积占用 | 每个运行时显示磁盘占用，「存储与目录」页汇总 |

**Python 的特殊处理**（取决于 §12 决策 1）：
- 默认最小粒度：标"必需"+ 灰蓝禁关，只允许在「内置便携 vs 系统 Python」之间切路径
- 进阶：可手动选择多个内置版本（额外 +80MB/版本）
- 进阶：可创建 venv（设置里有"为发布/为 MCP 各建一个 venv"按钮）

**开关语义要在 UI 上写清楚**（截图那句「允许使用随包提供的运行时工具」就是这个意思）：
> 关闭后，本应用将不再调用随包分发的二进制；若系统 PATH 中也没有对应程序，相关功能将被禁用。

### 5.3 审计中心（截图右下那一块）

- 记录**每一次对外部二进制的调用**：时间、运行时、命令（脱敏、超长省略）、退出码、耗时、触发来源（登录/发布/封面抽取…）、放行/拒绝结果；
- 后端新增 `runtime_audit` 表（SQLite，滚动保留最近 N 条 / N 天，默认 2000 条 / 30 天，可配置）；
- 支持 **导出日志**（JSON/CSV）与 **清空记录**（二次确认）；
- 实现方式：把 `subprocess.run/Popen` 收敛到一个 `util/runtime_exec.py` 包装层，统一走审计 + 超时 + 环境注入（顺带解决现在散落在 `ffmpeg_service`、`materials_bp` 等处的调用点）。

### 5.4 前端与外壳的桥接

- 外壳通过 `preload` 注入 `window.qfsShell = { platform, shellVersion, restartBackend(), openDataDir(), pickPath(), checkUpdate(), exportDiagnostics() }`；
- **运行时开关/路径/审计走 Python 后端 HTTP API**（这样网页模式同样可用），**仅原生动作走桥**；
- 前端统一 `const shell = window.qfsShell ?? null` 做能力探测：为 `null` 时隐藏「重启服务/打开目录/检查更新」，其余功能照常——**一份前端代码同时服务桌面版与网页版**。

### 5.5 新增后端 API（契约草案）

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/runtime/list` | 各运行时：id、名称、描述、必需性、开关、模式、解析到的路径、实测版本、状态、占用 |
| POST | `/api/runtime/{id}/toggle` | 启用/禁用（必需项拒绝） |
| PUT | `/api/runtime/{id}/path` | 设置模式与自定义路径 |

| GET | `/api/runtime/dependents` | 降级矩阵（谁依赖谁、哪些功能当前不可用） |

### 6.3 macOS 关键注意点

1. **CloakBrowser 放 bundle 外**（用户目录）是这套方案对 macOS 最大的简化：不需要给 `Chromium.app` 及其 5 个 Helper 逐一重签名，也不会因签名链条或 `Info.plist` 被改动而公证失败；
2. 若将来必须内嵌，则需：`mac.binaries` 显式列出所有嵌套 Mach-O、`entitlements` 加 `allow-jit` / `allow-unsigned-executable-memory` / `disable-library-validation`，并接受公证时间与失败率上升；
3. arm64/x64 分别产出 dmg，**不做 universal**；
4. 首次运行 Chromium 会弹「想访问其他应用的数据」类权限时，需要 `NSAppleEventsUsageDescription` 等 plist 文案预先写好；
5. **🟡 已选未签名 + 引导用户右键打开（§12 决策 6）**：没有 Developer ID + notarize，未签名的 `.dmg`/ `.app` 会被 Gatekeeper 拦。
   - **首次安装**：用户需在 `Finder` 右键 `QianFanSync.app` → "打开" → 在弹窗中点"打开"（一次）；
   - **每次启动/升级**（macOS 14+ 更严格）：可能需要在"系统设置→隐私与安全→仍要打开"再次确认；某些版本还需要 `xattr -dr com.apple.quarantine /Applications/QianFanSync.app`；
   - **风险**：新手用户极易在此步骤放弃；升级后首次启动必须重复操作；影响"桌面版降低用户门槛"的核心目标；
   - **缓解措施**：① 设置页提供"macOS 用户指引"图文教程；② 安装包内附 README + 一键脚本 `scripts/macos-unquarantine.sh`；③ 持续评估 Apple Developer ID（$99/年）的采购 ROI；
   - **未来切换路径**：拿到 Developer ID 后只需在 `electron-builder.yml` 打开 `notarize: true` 并填入 API Key，CI 加一道 `notarytool` 冒烟即可。

### 6.4 Windows 关键注意点

1. **🟡 当前未采购代码签名证书** → SmartScreen 首次启动会弹"未知发布者"，360/Defender 对隐身 Chromium 的误报会更频繁。**临时降级**：让用户点"仍要运行"或把目录加入白名单，**不能作为长期方案**。建议至少采购 OV 证书（~¥1500/年），EV（~¥12000/年）免 SmartScreen 即时报毒；
2. 隐身浏览器二进制极易被 Defender/360 误报 → 预案：提交误报申诉、安装包内提供「被拦截怎么办」帮助页、必要时可临时改走 CDN 下载（下载物不带安装包签名，误报面更小）；
3. `chrome.exe` 需真实文件路径（不能躺在压缩包/asar 里），且用户数据目录必须可写 —— 落在 `%LOCALAPPDATA%` 正好；
4. 卸载时询问是否保留 `data/`（用户有账号 cookie，误删代价极高）；
5. 进程收割：用 Job Object 或退出时 `taskkill /T /F`，避免残留 `chrome.exe` 占用端口/文件。

### 6.5 Linux 关键注意点

1. Electron 与 CloakBrowser 都依赖 Chromium 沙箱：新版发行版（Ubuntu 24.04+、部分国产系统）默认禁用非特权 user namespace → 需要 `chrome-sandbox` SUID（deb 安装脚本处理）或降级 `--no-sandbox`（有安全代价，需在界面上说明）；
2. AppImage 不带系统库 → 首启做依赖体检（复用 `start.sh` 里已有的包管理器探测逻辑：apt/dnf/pacman/zypper 提示）；
3. 国产化环境（麒麟/统信）如需支持，建议直接出 `.deb`（并考虑 arm64 版本，Python/Node 都有 linux-arm64 构建；CloakBrowser 暂无 arm64）；
4. 托盘需要 `libappindicator`，缺失时自动降级为「无托盘但窗口可用」。

## 7. 更新机制（双通道）

| 通道 | 内容 | 载体 | 频率 | 用户体验 |
|------|------|------|------|---------|
| **A. 主程序** | Electron 壳、图标文案、运行时管理器 | electron-builder + `latest.yml`（自建 CDN，支持差分 `blockmap`） | 低（月度） | 后台下载 → 提示「重启以更新」 |
| **B. 业务代码包** | `backend/`、`frontend/dist/`、`mcp/dist/` | 自建 CDN 的 `app-code-<version>.zip` + `manifest`（sha256、最小兼容 shell 版本） | 高（随时） | 启动时静默检查（几 MB），**下次启动生效**；保留上一版支持一键回滚 |
| **C. 运行时（可选）** | 四类内置环境 | §4.2 manifest 的 `cdn` 通道（默认 `enabled=false`） | 低 | 仅在用户主动开启 CDN 通道后启用；否则随主程序升级 |

要点：
- **B 通道就是现在 `git pull` 强更新的替代品**，但更安全：sha256 校验、解压到临时目录后原子替换、失败自动回滚；
- 保留 `git` 作为兜底（用户可切「从 Git 仓库更新」，适合内部/开发者）；
- 所有更新都需要**签名校验**（至少 sha256 + HTTPS；主程序走 electron-updater 的签名机制）；
- 版本兼容：`app-code` manifest 里声明 `minShellVersion`，避免新代码在旧壳里崩。
